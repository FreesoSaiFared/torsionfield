The GPU was there. WebGPU wasn't using it.

A local AI model was running far too slowly. The graphics panel said NVIDIA. The WebGPU adapter told another story.

We wanted an inexpensive local model to write draft headlines and relevance explanations for Torsionfield's research journal. Brave could load the model, and its GPU diagnostics listed an NVIDIA GeForce RTX 3060. That looked promising. Yet inference barely progressed and sometimes lost its GPU device.

The failure was not in the model's download, and a successful WebGPU compute demonstration did not settle the question either. The browser was executing that demonstration through Google SwiftShader, a CPU implementation.

The deceptive GPU reading

Chromium's browser-level GPU inventory and the graphics adapter used by a webpage are different measurements. Our first test verified NVIDIA in the browser's GPU list and then executed a compute shader that incremented 41 to 42. We prematurely treated the two observations as proof of NVIDIA-backed WebGPU.

A direct check of navigator.gpu.requestAdapter({powerPreference:'high-performance'}).info identified the adapter as vendor Google, architecture SwiftShader. The same result appeared for the default and low-power preferences. The CPU was doing the work.

That distinction is particularly important for agents that diagnose software by reading plausible system-status fields. The observation supporting a claim must measure the thing the claim is about.

The actual fix

We ran separate Brave profiles on i9ES, preserving the main browser. Chromium's WebGPU implementation-status documentation recommends an experimental Vulkan/ANGLE configuration for Linux X11. On this machine, the decisive flags were:

--enable-unsafe-webgpu
--ozone-platform=x11
--use-angle=vulkan
--enable-features=Vulkan,VulkanFromANGLE

With NVIDIA PRIME offload enabled, the WebGPU adapter itself reported NVIDIA / Ampere. A new independent compute test returned 42 from input 41. The browser was now executing on the card rather than merely listing it. The GPUWeb implementation discussion provides additional context on the Linux flags.

A model that produces text

We first reproduced browser-local text generation with SmolLM2 360M. It was quick, but it produced poor editorial copy. We then tested Qwen3.5 2B, quantized as q4f32 through WebLLM in an isolated local worker. The NVIDIA adapter on this host did not expose shader-f16, so the q4f32 variant was the appropriate tested configuration.

The generated text was no longer an empty response or an error. With no-thinking generation requested, it returned a headline and relevance paragraph. Those fields are useful drafts; matching an output format does not establish that all claims inside the draft are true.

Reproduce and challenge it

The machine-readable receipt records the configuration, negative controls, restart test, and repeated-run measurements. The source-controlled local workbench includes a prewarm launcher, adapter inspector, duplicate-tab recovery, and a bounded end-to-end acceptance test.

bash tools/webllm-personalizer/prewarm-i9es.sh
node tools/webllm-personalizer/check-gpu.mjs 9235
node tools/webllm-personalizer/accept-i9es.mjs

Our next question is not whether the model can emit plausible text. It can. The next experiment asks whether its interpretations improve source comprehension without inventing facts. That needs independent source validation, not another successful GPU benchmark.
